OAuth Starts
With a Problem

The core model: actors, endpoints, tokens, scopes, and consent —
before we touch a single line of JWT.

Goal of this deck: participants leave able to explain OAuth as delegated API access, identify the four actors, and know where OpenID Connect begins. Repeat the one-line definition often. Do NOT start from JWT.
The problem

Apps need to use other apps' data

A deployment dashboard wants to list your GitHub repos. Canva wants files from Google Drive. A Slack bot wants to post messages.

How does an app act on your behalf — without you handing over your password?

Anchor every example in everyday tools (GitHub, Drive, Slack, CLI) before banking. The question on screen is the whole reason OAuth exists. Ask the room: "What would you have to give the dashboard today to make this work?"
Why not just share the password?

Password sharing is the wrong shape

Give away the password

  • App can do everything you can do
  • App can store your password
  • No way to limit to one repo / one action
  • Revoking = change password (breaks everything)
  • App breached → your whole account is exposed

Give a scoped token

  • Limited to exactly what's needed
  • Password never leaves the trusted service
  • Scoped to one permission, e.g. repo:read
  • Revoke just this app, anytime
  • Token expires on its own

OAuth's core move: the client receives permission, not the user's password.

The phrase "wrong shape" sticks: a password is too much power in the wrong place. The token is the right-sized key. Everything else in OAuth exists to issue, scope, and validate that token safely.
Vocabulary

Framework, standard, flow

People say "OAuth" to mean three different things. Keep them separate.

TermWhat it isExample
FrameworkThe overall authorization modelClients, tokens, scopes, grants, endpoints
Standard / RFCThe official specRFC 6749 defines OAuth 2.0
Flow / grantOne way to get a tokenAuthorization Code, Client Credentials, Device

OAuth is the framework. RFCs define it. Flows are ways to use it.

This slide pre-empts a lot of confusion later. When someone says "is OAuth secure?", the answer depends on which flow, which client type, and how tokens are handled — not on "OAuth" as a single thing.
Running example

RepoBoard connects to GitHub

RepoBoard is a deployment dashboard. It wants to list your repositories — read-only.

  1. You click Connect GitHub in RepoBoard.
  2. RepoBoard sends you to GitHub to log in.
  3. GitHub asks: "Allow RepoBoard to read your repositories?"
  4. You approve. GitHub issues an access token to RepoBoard.
  5. RepoBoard calls the GitHub API with that token.
GET /user/repos
Authorization: Bearer <access_token>

RepoBoard never sees your GitHub password. We'll use RepoBoard for the whole workshop.

This is the same scenario as the Go demo app (client = repoboard-web). Tell participants we will literally run this flow later. Keep the access token abstract for now — format comes much later.
The cast

The four actors

Identify them by asking: Who owns the data? Who wants access? Who grants it? Who serves the API?

Drill this until automatic. In the Go demo these map to /client/* (Client), /authorize + /token (Auth Server), and /api/* (Resource Server). The four questions are the participant's portable tool for any new scenario.
Where requests go

Two endpoints do the real work

EndpointJobWho calls it
/authorizeUser logs in & approves accessThe browser (front-channel)
/tokenExchange a grant for an access tokenThe client server (back-channel)

Supporting endpoints you'll meet later:

/.well-known metadata /introspect /revoke

Front-channel = through the browser, more exposed. Back-channel = server-to-server, more protected. Remember which is which — it drives every security decision.

Plant the front-channel vs back-channel idea now; it returns in PKCE, in security controls, and in FAPI. The whole of OAuth security is about not letting valuable secrets travel through the exposed front-channel.
The token

What the access token means

It IS

  • A credential the client sends to the API
  • Proof of permission
  • Scoped, expiring, revocable
  • Checked by the resource server on every call

It is NOT

  • The user's password
  • Proof of who the user is (that's the ID token, later)
  • Automatically a JWT
  • Safe to leak — it's a bearer credential
GET /user/repos
Authorization: Bearer <access_token>
"The access token represents permission, not the user's password" — say it out loud and have the room repeat it. Resist any question about token format here; that is Deck 4. Today the token is an opaque permission slip.
Scope

Scope limits what the client may ask for

Scope is the size of the key. Ask for the minimum — least privilege.

repo:read repo:write read:calendar write:message read:balance

RepoBoard only needs repo:read — so that's all it should request. Asking for repo:write would be over-reach.

Tie scope back to the "wrong shape" slide: scope is exactly the mechanism that makes the token the right size. Good question for the room: "What's the blast radius if RepoBoard's token leaks with repo:read vs admin?"
Audience

Audience says which API the token is for

A token minted for the GitHub API must not be accepted by a payments API. Audience binds the token to its intended resource server — a key check we'll formalize in token validation.

Audience prevents token "confused deputy" reuse across APIs. Don't over-explain validation here; just seed the idea that the resource server must confirm the token was meant for it. Full validation checklist is Deck 4.
Consent

The user approves limited access

github.com · Authorize RepoBoard

RepoBoard would like to:

Read your repositories

Signed in as @alya

Authorize Cancel
  • Consent happens on the authorization server, not in the client.
  • The user sees exactly which scopes are requested.
  • Approve or deny — the user stays in control.
  • Machine-to-machine flows often have no consent screen.
Consent is a user-delegated concept. Foreshadow Client Credentials (Deck 3): no human, no consent screen — the token represents the service itself. That contrast lands better once they've seen the consent screen here.
The boundary that confuses everyone

OAuth vs OpenID Connect

OAuth 2.0OpenID Connect
PurposeAuthorizationAuthentication
QuestionWhat can this client access?Who is the user?
Main tokenAccess tokenID token
ExampleConnect GitHub repos / Drive files"Log in with Google"

Wants to call an API? → OAuth. Wants to know who you are? → OpenID Connect.

Many products do both: sign you in (OIDC) and request API permissions (OAuth).

The single most common confusion in the whole course. "Login with Google" feels like OAuth but is really OIDC. The demo app uses go-oidc and can issue an ID token — we'll point that out when we extend it.
Client types

Can the client keep a secret?

Public client

  • Cannot safely store a secret
  • Browser SPA, mobile app, CLI
  • Needs PKCE (Deck 2)

Confidential client

  • Can keep a secret / private key
  • Server-side web app, backend service
  • Authenticates at /token

This one question — "can it keep a secret?" — decides how a client authenticates and which protections it needs.

In the Go demo: repoboard-web and deploy-cli are public; order-service is confidential. Connect this slide to the demo's three registered clients. It sets up exactly why PKCE exists in the next deck.
Implementation walkthrough

One config reveals every actor

CLIENT_ID=repoboard-web
AUTHORIZATION_ENDPOINT=https://github.com/login/oauth/authorize
TOKEN_ENDPOINT=https://github.com/login/oauth/access_token
RESOURCE_API=https://api.github.com
REDIRECT_URI=https://repoboard.example.com/oauth/callback
SCOPES=repo:read
  • CLIENT_ID → the Client
  • AUTHORIZATION_ENDPOINT + TOKEN_ENDPOINT → the Authorization Server
  • RESOURCE_API → the Resource Server
  • SCOPES → requested permission · REDIRECT_URI → where the browser returns
Read the config line by line with the room and have them name the actor each line belongs to. This is the bridge into the live Go demo, whose config looks just like this.
Checkpoint · Lab 1

Map the actors

For each scenario name the Resource Owner, Client, Authorization Server, Resource Server:

  1. Canva imports photos from Google Drive
  2. A VS Code extension creates GitHub issues
  3. A Slack bot reads channel messages
  4. A CI pipeline pulls packages from a private registry
  5. A mobile app connects to Fitbit health data

Discuss before revealing answers. Watch for the OIDC trap: which of these is really about identity?

Let participants struggle for a minute each. #4 has no human resource owner (the org/system owns it) — great discussion point. None of these is primarily login, so none is OIDC — but ask anyway to test the boundary.
Recap

The mental model in four questions

QuestionRepoBoard answer
Who asks for access?The Client (RepoBoard)
Who approves?The Resource Owner (you), at the Authorization Server
Who issues the token?The Authorization Server (GitHub)
Who validates it?The Resource Server (GitHub API)

OAuth lets an app access an API with limited permission — without ever receiving the user's password.
